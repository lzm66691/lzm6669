## 1. 要解决的问题

用户把 DSH 当工作台用，但没有「谁负责什么」的固定分工。原状是：需求、实现、验证全由同一个 agent 在同一个上下文里做完。

**核心问题：生产者与评审者不能是同一个人。** 同一个上下文里既写又验，等于自己给自己发合格证——验收环节形同虚设。

---

## 2. 约束

1. **DSH 物理约束**：AgentTeams 的团队干完即归档，成员不会常驻
   → 部门只能是「**常设定义 + 临时实例**」，不可能有常驻部门
2. **用户是新手**：体系必须能一句话说清；不能要求用户自己记流程
3. **跨会话**：会话会被压缩或重开 → 关键信息必须落盘，不能只活在对话里
4. **多个工作区**：用户有 3 个工作区 → 部门定义与台账必须全局共用

---

## 3. 选定方案：三部 + 升格规则 + 文件化关卡

| 部门 | 管阶段 | 不许干什么 |
| --- | --- | --- |
| 研究部 | 1 想清楚 / 2 定规格拆任务 | 不许写实现代码 |
| 工程部 | 3 动手做 | 不许自己验收自己的活 |
| 质检部 | 4 验证与评审 | 只读，不许改产物 |
| （秘书） | 5 收尾与交接 | — |

**判据**：每个阶段都必须有明确的「谁负责、产出是什么、出口判据是什么」。三部正好覆盖阶段 1-4，且保证评审独立于生产；阶段 5 是收尾文书工作，单独立一个部门不划算。

（曾比较过其他部门划分方案，最终按「每个阶段都要有人负责、且评审必须独立」这两条判据收敛到三部。）

**升格规则**：某类活**连续出现 3 次** → 升格为独立部门。
理由：避免一开始就把编制拍死；先让重复模式自己浮现，再按需扩编。

---

## 4. 权限边界

| 事项 | 谁定 |
| --- | --- |
| 日常调度（派活 / 重试 / 叫停 / 换人） | 秘书自定 |
| 改范围 / 超预算 / 对外交付 | **必须问用户** |

理由：日常调度频繁，每次都问会让用户变成瓶颈；后三类不可逆或有外部后果，必须留人工闸门。

---

## 5. 关卡形状

两道硬关卡 + 三处留痕，见 `docs/workflow/gate.yaml`。

| 关卡 | 要见什么 |
| --- | --- |
| 2 → 3 | 规格文件路径 + 任务清单（每项有负责人、验收标准、依赖边） |
| 4 → 5 | 验证命令与输出 + `reviewer_report:` 质检报告**原文路径** |

### 关键设计：为什么要求填「文件路径」而不是「通过 / 不通过」

`stage4_to_stage5` 必须填 `reviewer_report:`，**空 = 未通过**。

如果关卡只要求一个 `passed: true`，秘书可以自己写一句「我检查过了」就过闸——这正是要堵的漏洞。
要求填**文件路径**，是因为路径**可以被检查**：文件在不在、内容是不是真的命令加输出。
布尔值无法被检查，路径可以。

同一逻辑贯穿：「结论跟着证据走」在关卡上的落地形式，就是**强制交出可核验的路径**。
